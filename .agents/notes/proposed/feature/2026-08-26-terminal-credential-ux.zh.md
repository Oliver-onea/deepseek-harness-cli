# Agent Note：终端凭据体验——无 key 失败的可见性，以及在终端里设置密钥

Status: proposed

[English](2026-08-26-terminal-credential-ux.md) | 中文

## 问题

新用户在没有 API key 的情况下于终端启动 `dsh`，可以进入会话——这一点是对的，也要保留——但发送提示词后什么都没有：没有回答、没有报错、没有任何提示。同样的场景下，headless 应用已经能打印出可据以处理的 `MISSING_CREDENTIAL` 失败。终端两端其实都有相应机制：agent loop 会以 error 原因记录 `turn/end`，transcript 也具备 error 通知的色调——但没有任何东西把失败的回合折叠成一条被绘制的行，于是这个失败从未出现在屏幕上。

这样的用户接下来也没有任何办法就地自救。LLM 错误里的凭据指引让终端用户去打开「web 版 Models 页面」——一个他们根本没在运行的界面——而且尽管凭据服务本可以写入受管的 `$DSH_HOME/.credentials.yaml` 存储，却没有任何 CLI 标志、斜杠命令或子命令暴露这个写入路径。

## 方案

1. **transcript 绘制失败的回合。** `Transcript` 会把原因为 error 的 `turn/end` 折叠为一条 error 色调的通知，携带 code 与可据以处理的消息——与 headless 打印的事实一致。针对未变化失败的再次发送会替换掉相同的通知而不是再堆一条；该替换只回溯跨越 `user` 条目，因此中间出现的任何 assistant、tool 或其他通知都会让较早的失败保持可见。实时渲染与 `--resume` 回放对同一个已记录事件执行同一套折叠，因此失败可以跨越 resume 存留，而无需第二种事件类型。
2. **终端进入凭据 seam 的写入路径。** 新包 `@deepseek-ai/dsh-command-credential` 通过 `commands` 服务注册一个全局 `/credential` 命令，由 base bundle 与 `credentials-local` 并列挂载。`/credential <REF>` 以不含值的 `describe` 事实作答；`/credential <REF> <value>` 通过 `ctx.credentials.set` 存储——写入受管存储，绝不写 `.env`。该定义设置 `recordInput: false`，因此 `command/run` 省略 `args`；所有成功与错误文本都不含值；还有一道脱敏守卫，在提供方失败信息成为命令输出之前把值从中抹去。当启动环境以只读方式遮蔽该引用时，命令返回服务本身的显式拒绝，而不是静默无效；描述路径也会预先就遮蔽给出警告。
3. **注册不能等待提供方。** 该插件只注入 `commands`，在执行时读取 `ctx.get('credentials')`。若以凭据提供方为门槛，注册会被推迟到该提供方加载完成——而在快速启动的终端里，那时 `/help` 早已应答——命令就会错过那个让它可被发现的列表本身。对于未挂载任何凭据服务的组合，则在使用时给出清晰错误。
4. **指引诚实地点名两个写入者。** `llm-deepseek` 与 `llm-pi-ai` 的 `MISSING_CREDENTIAL` 消息，以及 `assertUsableApiKey` 中的两处 `INVALID_CREDENTIAL` 文案，现在都表述为：通过凭据服务存储该引用——在终端用 `/credential <REF> <value>`，在 web 应用里由 Models 页面写入——或者在启动环境中导出。这些文案在各表面之间共享，因此各自保留了另一表面的用户能够触及的那个写入者。

## 备选方案考量

- **为失败引入新的会话事件或通知类型。** 拒绝：带 error 原因的 `turn/end` 已经记录了失败，且「模型可见 ⟺ 已记录」通过绘制既有事件即可满足。第二种事件会重复状态，并且仍需要同一套 resume 折叠。
- **带默认引用的 `/key <value>` 命令。** 拒绝：单 token 输入存在歧义——`/key DEEPSEEK_API_KEY` 会把字面的引用名当作机密存进去。`/credential <REF> [<value>]` 解析是确定的，并且既能描述也能存储，与 seam 的 `describe`/`set` 表面一致。
- **把命令注册进 `credentials-local` 内部。** 拒绝：这会把 UI 角色塞进提供方，给文件后端加上 `dsh-agent`/`dsh-session` 对等依赖，并把命令可用性耦合到提供方的加载顺序；仓库的惯例是每个命令一个细粒度包（`command-feedback`、`command-goal`、`command-compact`）。
- **对所输入的机密做掩码。** 拒绝：出厂的终端输入表面都不支持掩码输入，因此命令把值作为参数接收，并在 README 中说明输入行不做掩码，而不是假装掩码。
- **在同一变更里一并更新 `web-search-deepseek` 的凭据消息。** 暂缓：它不是终端凭据失败所展示的消息之一，且已提供环境与字面配置两种替代。后续可用「两个写入者」的措辞与其对齐。

## 验收标准

- 无 key 启动 `dsh` 仍然受支持；在没有可解析凭据时发送提示词会绘制出一条 error 通知，携带 code 与可据以处理的消息，且会话保持可用。
- 针对未变化失败的再次发送只保留一条可见通知。
- 该失败能从已记录的 `turn/end` 重建，跨越 `--resume` 存留。
- `/credential` 可在 `/help` 中被发现，经由凭据服务写入受管存储，绝不写 `.env`，并且在被环境遮蔽时报告该情况而不是静默无效。
- 机密不出现在任何已记录事件、结果文本、transcript 行或模型请求中。
- 凭据指引不再把 web 版 Models 页面作为终端用户唯一的选择。

## 风险

- 终端输入行不掩码所输入的值：作为命令参数键入的机密在输入时可见，并保留在终端回滚缓冲里。README 已说明这一点；掩码输入推迟到某个终端输入表面提供支持为止。
- `/help` 快照依赖每个命令插件都已完成注册；加载缓慢的注册原则上可能截断列出的名单。无 key 场景在快照前先用一条后续通知让视图稳定，且注册刻意避免等待凭据提供方。
- `web-search-deepseek` 的凭据消息仍只点名 web 写入者；后续应将其与「两个写入者」的措辞对齐。

## 验证

- 针对该命令的单元测试与真实 Loader 组合测试，包括断言机密不出现在任何已记录事件、结果文本或渲染行中，以及被遮蔽的引用会被报告。
- 经由出厂终端配置的无 key PTY 快照：无 key 发送后的失败通知、重复发送后仅一条通知、resume 回放、包含 `/credential` 的 `/help` 列表，以及以受管文档落盘为终点的存储流程。
- 重新录制的 headless 无 key 夹具，固化新的指引文案。
