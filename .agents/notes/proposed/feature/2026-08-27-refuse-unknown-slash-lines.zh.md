# Agent Note: 拒絕未知的斜線行，而不是把它送給模型

Status: proposed

[English](2026-08-27-refuse-unknown-slash-lines.md) | 中文

## 問題

終端把命令登錄表無法解析的任何一行都當成對話送給模型。`classifySubmission` 對每一行未解析的輸入都回傳 `{ kind: 'prompt' }`，包括長得像斜線命令的那些。

這是一條密鑰外洩路徑。`/credential <REF> [<value>]` 以命令參數接收 API key，而該命令是有保護的：它宣告 `recordInput: false`，讓命令服務把參數排除在被記錄的事件之外，並且把每一則渲染出來的供應商錯誤都送進 `redactValue`。**兩道保護都掛在「已解析的命令」上。** 讀者把命令名打錯就什麼都解析不到，兩道保護都不生效，整行變成一則提示。

在整合分支上以 mock 供應商實測，送出 `/credentail DEEPSEEK_API_KEY sk-…`：

- 該金鑰以明文渲染在對話記錄中，
- 並且被夾帶在**兩次**送出的模型請求裡。

面對真實供應商時，金鑰就離開了這台機器。少打一個字母就足夠。

## 提案

給路由第三種結果。若一行的開頭符記可以解析成命令名（`commandNameOf`：一個斜線、一個識別字、然後一個詞邊界），但登錄表無法解析它，則歸類為 `{ kind: 'unknown-command', name }`。Shell 畫出 `Unknown command: /<name> — run /help for the list`，不送出任何東西。

兩項例外讓既有行為保持完整：

- **使用者可呼叫的技能正是以 `/名稱` 呼叫的，必須仍然以提示的形式抵達模型。** 技能不是登錄表命令，所以 shell 在拒絕之前先查技能目錄。只有這條路徑付出這次查詢；已解析的命令與一般文句都不會走到。目錄讀取若拋出例外則回答「是」——把讀者原本當成技能的一行轉發出去是可回復的，因為目錄一時不可用就拒絕所有技能則不是。
- **沒有掛載命令登錄表的組合，根本不存在「相對於什麼而言未知」**，所以那裡的每一行都維持為對話。

`commandNameOf` 要求識別字之後必須是詞邊界，因此只是以路徑開頭的文句（`/usr/bin/env is where env lives`）不受影響。

拒絕訊息只回顯解析出的名稱。參數——也就是密鑰——永遠不會被畫出來。

## 曾考慮的替代方案

**維持現狀，倚賴 `recordInput: false`。** 否決：該旗標是「已解析命令」的屬性，而整個失效點正是什麼都沒解析到。就構造而言它不可能涵蓋這個打錯字的情況。

**把打錯的字模糊比對到已知命令並提示最接近的一個。** 訊息更好，但它沒有回答安全問題——一個離所有命令都夠遠的名稱仍然會落到模型那裡。值得日後疊加在拒絕之上；不能替代它。

**不再以命令參數接收密鑰，改用互動面板讀取。** 這是更強的修法：從未被打在送出行上的密鑰，不可能被路由到任何地方。它也是更大的改動，而且幫不了那位出於其他工具習慣而打出 `/credentail` 的讀者。建議作為後續項；拒絕才是現在堵住已證實漏洞的做法。

**拒絕所有未解析的斜線行，不給技能例外。** 最簡單，也是第一次嘗試的做法。它打斷了技能呼叫——有五個測試明確描述該行為——因為技能抵達模型的方式，恰恰就是成為一行未解析的斜線行。

## 驗收標準

1. 登錄表無法解析的命令形狀行，產生一則本地錯誤通知，且不產生任何模型請求。
2. 拒絕訊息只回顯命令名，絕不含參數。
3. 命名了使用者可呼叫技能的 `/名稱` 仍然抵達模型。
4. 以路徑開頭的文句，以及沒有登錄表的組合下的每一行，仍然抵達模型。
5. PTY 探針確認打錯字的憑證行對外請求次數為零。

## 風險

- **技能查詢跑在拒絕路徑上。** 那是一次目錄讀取，只發生在未解析的命令形狀行上，而 `/` 選單本來就執行同一次讀取。若某個部署的目錄很慢，打錯的命令會變成「拒絕得慢」，而不是「判斷錯誤」。
- **想把字面上的 `/word …` 送給模型的讀者現在必須改寫。** 先前沒有任何行為倚賴這一點；拒絕訊息點名了 `/help`，所以復原方式是看得見的。
